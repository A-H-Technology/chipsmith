# 7-series block RAM: RAMB18E1s from the M4K mapper's analysis, a model checked against Vivado's, bitstreams read back half by half

The Zybo build put every memory with synchronous reads into registers and multiplexers; the DE2's has mapped them onto M4K blocks since 2026-10-28 (README, "M4K RAM blocks"). The 7-series block RAM is the same kind of block, a quarter larger: two ports with their own clocks, widths x1 to x18 (x36 in simple dual port mode), byte enables, output registers, initial contents. What differs is the read-during-write behaviour, chosen per port (WRITE_FIRST, READ_FIRST, NO_CHANGE), and what the other port reads on the same edge: the old data only if the writing port is READ_FIRST, undefined otherwise (UG473).

So:

- **Synthesis follows the M4K mapper** (chipsmith-cyclone2 `synth/m4k.rs`): the same port analysis (widening mixed-width ports, single, simple and true dual port roles, two writes colliding resolved in logic, deep and wide arrangements). It lives in `chipsmith_xc7::synth::bram`, not shared with the Cyclone II's: the block semantics differ in every function past the port analysis, and the DE2's mapper must keep building byte-identical RBFs while another branch changes the DE2 synthesis. Each port's write mode follows from the RTL: READ_FIRST where the other port reads the word's old data, WRITE_FIRST where the port's own read sees its new data; where both hold, the port is READ_FIRST and its own read of the new data is a register of the written data in logic. Vivado builds a true dual port with both ports WRITE_FIRST and leaves the same-edge cross read undefined; chipsmith's matches the RTL there.
- **RAMB18E1s only.** A RAMB36E1 holds no more than its two halves, and its byte enables don't split over the halves the way two RAMB18E1s' do (each half's four WE pins are byte lanes of the 36-bit word, every other bit). Vivado reports a RAMB36E1 where chipsmith uses two RAMB18E1s; the BRAM tiles used are the same. A RAMB36E1 instantiated in a design is still built.
- **One configuration type** (`chipsmith_xc7::bram::Config`) that synthesis writes as the primitive's parameters and the packer, FASM writer and decoder read back; an invalid combination (x36 on a TDP RAMB18E1, an SDP block writing on port A) is refused when parsed.
- **The behavioural model is chipsmith's own** (`crates/chipsmith-xc7/src/sim.v`): yosys' `cells_sim.v` has RAMB18E1 only as a timing blackbox. It is checked against Vivado's unisim models on random configurations and stimulus (`tests/models.rs`, which runs where Vivado is installed): 2.84 million output bits over 40 runs of six blocks, none different; 2,277 bits are x in chipsmith's model where Vivado's gives a value (a collision the model calls undefined). Where the two disagree outside what netlists use (a port reading and writing at two widths; a READ_FIRST write of some bytes read by a narrower port on the same edge, where unisim gives the new data and UG473 the old), synthesis doesn't build it.
- **The bitstream is read back half by half.** A RAMB36E1 is two RAMB18 halves on the same tile wires, so the decoder makes a RAMB18E1 of every half in use. Its encoding was taken from Vivado's own bitstreams read by bit2fasm: the width bits (as openXC7's nextpnr writes them), RDADDR_COLLISION_HWCONFIG, and INIT/SRVAL held bit-reversed in an x18 layout (found with one-hot INIT values); the contents in order. Ten of Vivado's twelve test bitstreams decode to netlists that co-simulate against their RTL; the other two are Vivado's true dual port (x where Vivado leaves the cross read undefined) and LUT RAM, which the decoder doesn't read.

## Considered options

- Generalise the M4K mapper into chipsmith-synth with the block as a parameter: one mapper, but a large change to the DE2's synthesis under another branch's work, and every block-specific function would grow a branch per device.
- yosys' `memory_libmap` with its `brams_xc7` description as the reference implementation: what it emulates and what it doesn't is close to this, but chipsmith's synthesis no longer runs yosys, and the M4K mapper already answers the same questions in the same netlist IR.
- Use Vivado's unisims in the co-simulation directly: they are licensed and not in the devshell; the tests would need Vivado. Checking chipsmith's model against them once per change keeps the tests free of it.
- RAMB36E1s where Vivado uses them: the decoder would have to model the halves' byte lanes per width, for no saving in tiles.

## Consequences

- The DE2 standard applies: every shape is co-simulated against its RTL (`crates/chipsmith-xc7/tests/synth.rs`, `block_ram_shapes`) and through the bitstream (`crates/chipsmith/tests/xc7_bitstream.rs`, `block_ram`); the board check is owed.
- Not mapped: asynchronous resets of the read data (logic), memories of 64 words or fewer (logic; Vivado puts them in LUT RAM), RAMB36E1 cascades and ECC.
- What the board would settle: the power-up value of a block's output register, the READ_FIRST cross read of a part-written word by a narrower port, and the halves' byte lanes.
